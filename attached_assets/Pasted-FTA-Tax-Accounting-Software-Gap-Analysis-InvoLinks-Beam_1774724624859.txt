PRIORITIZED DEVELOPMENT ROADMAP FOR FTA ACCREDITATION
PRIORITY 1 — BLOCKERS (must be built before accreditation submission)
P1-A: General Ledger Table in FAF Export
The FTA FAF specification requires a [GeneralLedger] table section. The GL data exists in JournalEntryDB / JournalEntryLineDB (debit/credit amounts, account codes, source document references) but is not serialised into the FAF CSV. Add a 5th table to FTAAuditFileGenerator._build_faf_content() with columns: EntryDate, EntryNumber, AccountCode, AccountName, DebitAmount, CreditAmount, Currency, AmountAED, SourceDocumentType, SourceDocumentRef, Description.

P1-B: VAT Return Exportable Files (.xlsx and .xml)
The VAT Return is generated and displayed on-screen only. FTA accreditation requires the return to be downloadable in both .xlsx and .xml format. Build two new endpoints:

GET /vat-return/{id}/export/xlsx — using openpyxl (already a dependency)
GET /vat-return/{id}/export/xml — a structured XML matching FTA's declared schema
Both files must embed: vendor TRN (InvoLinks), company name, software name (InvoLinks), software version, and the client company's TRN.

P1-C: Software Name & Version in FAF CompanyData
Add two columns to COMPANY_DATA_HEADERS: SoftwareName and SoftwareVersion, and populate them from an application constant (e.g., SOFTWARE_NAME = "InvoLinks", SOFTWARE_VERSION = "1.0.0"). Also embed the reporting period start/end dates in the file header block.

P1-D: Forced Password Change on First Login
Add a must_change_password: bool = False column to UserDB. Set it to True for all invited users at invite-acceptance time. On any authenticated API call, if must_change_password is True, return HTTP 403 with {"detail": "password_change_required"}. The frontend must intercept this and redirect to a change-password page before allowing navigation.

PRIORITY 2 — SIGNIFICANT GAPS (needed for full compliance)
P2-A: AED Conversion Enforcement on Foreign-Currency Invoices
Make total_amount_aed non-nullable when currency_code != "AED" at the API validation layer. The FAF and VAT return must report amounts in AED. Add a validation guard in POST /invoices and PUT /invoices/{id} and propagate AED values to FAF SalesData / PurchaseData rows.

P2-B: Weekly and Annual Reporting Periods
Add period_type=weekly and period_type=annual to the /reports/periodic endpoint logic. Update PeriodicReport.jsx to expose these options in the period-type selector.

P2-C: Report Export in XLSX and PDF
PeriodicReport.jsx currently exports CSV only. Add .xlsx export (openpyxl already available) and .pdf export (reportlab/weasyprint, already used for invoice PDFs). Apply the same to GL Trial Balance and General Ledger pages.

P2-D: GL Journal Entry Edit/Delete Guard
Confirm or add an explicit check on any PUT /journal-entries/{id} or DELETE /journal-entries/{id} endpoint that prevents modification of posted (non-draft) journal entries — mirroring the invoice edit guard.

P2-E: Automated Database Backup
Implement a scheduled backup mechanism:

A cron-driven pg_dump script (or AWS RDS automated snapshot if cloud-hosted)
Store backup archives to a durable location (S3 / equivalent)
Log backup events to a BackupLogDB table with timestamp, size, and checksum
Provide a POST /admin/backup/restore endpoint (admin-only) to trigger a restore
PRIORITY 3 — RECOMMENDED IMPROVEMENTS
P3-A: Ad Hoc Report Generation
Add a free-form date-range report endpoint (e.g., GET /reports/adhoc?from=&to=&type=) that supports arbitrary periods beyond fixed month/quarter boundaries. Expose in the UI alongside the periodic report.

P3-B: Customer Data Retention Policy Enforcement
Add a documented retention policy: prevent deletion of company/customer records that have associated invoices within the 5-year FTA retention window. A soft-delete guard on DELETE /customers/{id} that checks for linked invoices within the retention period would satisfy this requirement.

P3-C: Periodic Integrity Verification
Implement a background job (e.g., a scheduled FastAPI startup task or cron) that re-verifies the SHA-256 hash chain for issued invoices. Log any chain breaks to AuditLogDB with action="INTEGRITY_CHECK_FAILURE". This satisfies the FTA requirement for long-term data integrity assurance.

P3-D: XML VAT Return Schema Alignment
When building the XML export (P1-B), validate the output against the FTA's published XSD schema. The UBL XML generator already has XSD support scaffolding (UBL_XSD_PATH) — enable and extend it for VAT return XML.
