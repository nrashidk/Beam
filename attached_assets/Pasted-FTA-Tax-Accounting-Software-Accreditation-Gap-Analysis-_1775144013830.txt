A-3. QR Code on Invoice
⚠️ Partially present — content is non-compliant with FTA specification

What exists:

PDF: pdf_invoice_generator.py:160-188, 634-635 — QR code generated via qrcode library, printed on PDF.
API: main.py:11134-11184 — GET /invoices/{id}/qr-code endpoint returning PNG.
Frontend: src/components/InvoiceDeliveryActions.jsx:58 — QR image via external api.qrserver.com.
What is missing:

The QR code encodes a plain URL ({base_url}/invoices/view/{share_token}) pointing to the InvoLinks platform.
The FTA specification (aligned with ZATCA Phase 1) requires the QR code to encode TLV (Tag-Length-Value) encoded fields in Base64, containing at minimum:
Tag 1 — Seller name
Tag 2 — Seller TRN
Tag 3 — Invoice date/time (ISO 8601)
Tag 4 — Invoice total (incl. VAT)
Tag 5 — VAT amount
A URL-only QR cannot be verified offline by an FTA auditor or scanner tool.
No TLV encoding function exists anywhere in the codebase (Grep for TLV, tlv, ZATCA returns zero matches in utility files).

B-2. UAE PINT-AE CustomizationID
⚠️ Partially present — uses generic PEPPOL BIS 3.0 ID, not UAE-specific PINT-AE ID

What exists:

ubl_xml_generator.py:100-113 — Hardcoded to:
CustomizationID: urn:cen.eu:en16931:2017#compliant#urn:fdc:peppol.eu:2017:poacc:billing:3.0 (PEPPOL BIS 3.0)
ProfileID: urn:fdc:peppol.eu:2017:poacc:billing:01:1.0
What is missing:

The UAE PINT-AE specification requires the CustomizationID to reference the UAE-specific profile: urn:peppol:pint:billing-1@ae-1 (or equivalent UAE-issued PINT-AE URN).
The current ID is the generic EU/global PEPPOL BIS 3.0 identifier — an FTA validator will reject invoices with the wrong customization URN.
B-3. Tax Category in XML (per Line Item and Header)
⚠️ Partially present — tax category hardcoded to 'S' (Standard Rate) regardless of actual tax code

What exists:

ubl_xml_generator.py:296-304 — cac:TaxTotal/cac:TaxSubtotal/cac:TaxCategory/cbc:ID is hardcoded to 'S'.
ubl_xml_generator.py:385-390 — cac:InvoiceLine/cac:Item/cac:ClassifiedTaxCategory/cbc:ID is also hardcoded to 'S'.
What is missing:

For zero-rated invoices (ZR), the category ID must be Z (not S) and Percent must be 0.00.
For exempt invoices (ES), the category ID must be E and Percent must be absent/0.00.
For reverse-charge (RC), the category ID must be AE.
For out-of-scope (OP), the category ID must be O.
The tax_category field exists on line items in the DB (TaxCategory enum: S, Z, E, O) and is passed to the XML generator in line_items_data, but the XML generator ignores it and hardcodes 'S'.

B-5. XML Digital Signature (XMLdsig / XAdES)
⚠️ Partially present — signature is detached (not embedded in XML), and uses self-signed keys

What exists:

main.py:10620-10757 — issue_invoice() generates invoice hash, XML hash, RSA signature, stores in DB columns (signature_b64, xml_hash, signing_cert_serial, signing_timestamp).
