The FTA PINT-AE specification requires a TLV-encoded QR code containing: (1) Seller name, (2) Seller TRN, (3) Invoice date/time, (4) Invoice total (incl. VAT), (5) VAT total — encoded in Base64 TLV format (as per Saudi ZATCA model adopted in some PINT-AE guidance)

A-1  Sequential, Unique Invoice Numbering
     STATUS: ⚠️  Partially present

     What exists:
       main.py:7034 — generate_invoice_number() uses type-specific prefixes:
         TI-XXXXX (380), TCN-XXXXX (381), DN-XXXXX (383), CI-XXXXX (480), CN-XXXXX (81)
       Numbering is per-company, per-type, five zero-padded digits.

     What is missing:
       The counter is based on db.query(InvoiceDB).count() for that type.
       If an invoice is deleted or hard-cancelled, count() drops, the next
       generated number can DUPLICATE a previously assigned number.
       FTA requires gap-free sequential numbers.  A dedicated, never-decremented
       sequence (e.g. a PostgreSQL SEQUENCE or a CompanyCounter table with
       pessimistic lock) is required.  No such sequence table was found.

B-3  Credit/Debit Note VAT Impact on Form 301
     STATUS: ⚠️  Partially present — Box 2 mapping is INCORRECT

     The FTA Form 301:
       Box 1 = Standard-rated supplies (output VAT base)
       Box 2 = Tax refunds provided to TOURISTS under the Federal Tourist
               Refund Scheme (a completely separate scheme, not credit notes)
       Box 3 = Output VAT on Box 1

     What the code does:
       main.py:16307–16308 — Box 2 is populated with VAT from credit notes
         (type 381) and debit notes (type 383).
       main.py:1339 — VATReturnDB.tax_refunds_provided comment says
         "tourist refunds" but is fed credit note VAT.

     This is INCORRECT.  Credit note VAT adjustments should REDUCE Box 1
     (the taxable base is net of credit notes) and correspondingly reduce
     Box 3 (output VAT).  Putting credit note VAT into Box 2 overstates
     tourist refunds and misstates both Box 1 and Box 3, leading to
     incorrect net VAT payable (Box 13).

     Only genuine tourist refund scheme transactions should go into Box 2.
     If tourist refunds are not applicable, Box 2 = 0.

SECTION E — QR CODE REQUIREMENT
════════════════════════════════════════════════════════════════════════════════

E-1  QR Code on PDF Invoices (FTA Technical Specification)
     STATUS: ⚠️  Partially present — QR code exists but wrong format

     What exists:
       pdf_invoice_generator.py:160 — generate_qr_code() creates a QR code.
       pdf_invoice_generator.py:633–637 — QR code is included in PDF.
       main.py:11133–11139 — /invoices/{id}/qr endpoint generates share link.
       pdf_invoice_generator.py:599 — QR encodes a public_url (share URL).

     What is required:
       The UAE FTA e-invoicing technical specification requires the QR code
       to encode a TLV (Tag-Length-Value) byte sequence containing:
         Tag 1 (1 byte): Seller name          (UTF-8)
         Tag 2 (1 byte): Seller TRN           (UTF-8)
         Tag 3 (1 byte): Issue date/time      (ISO 8601)
         Tag 4 (1 byte): Invoice total (incl. VAT)
         Tag 5 (1 byte): VAT total
       This is the same TLV scheme used by Saudi Arabia (ZATCA Phase 1)
       and adapted for UAE PINT-AE.

       The current implementation encodes a plain HTTPS URL — not TLV data.
       A public URL is NOT acceptable as the sole QR code content under
       the FTA spec (it must be scannable without internet access to return
       the TLV fields).

     Searched for: TLV, tlv_encode, base64.*hash, QR.*TLV — no matches found.
     What needs to be built:
       • tlv_encode() function producing the byte sequence above
       • Integration in pdf_invoice_generator.py to embed TLV QR instead of URL
