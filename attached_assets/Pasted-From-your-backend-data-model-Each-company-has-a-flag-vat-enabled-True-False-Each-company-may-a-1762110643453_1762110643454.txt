From your backend data model:

Each company has a flag vat_enabled (True/False).

Each company may also have a trn (their VAT registration number in UAE).

Invoices have different “types,” like:

"380" = Tax Invoice (VAT invoice)

"480" = Commercial Invoice (out of scope of VAT)
These are defined on the backend as InvoiceType enum values. 
GitHub

So conceptually:

If vat_enabled = False, you’re supposed to issue something like a Commercial Invoice / no VAT.

If vat_enabled = True, you’re allowed to issue a Tax Invoice and show VAT rates, TRN, etc.

That part is by design. 👍

Now let’s look at what’s actually happening for you.

Scenario 1: Company with VAT NOT enabled → "regular invoice with no tax" → you get an error

What you expect:

Create a simple invoice with line items, no VAT, no TRN.

System should let you issue a non-tax invoice (likely invoice type 480, “Commercial Invoice / Out of Scope”).

What you’re getting:

A modal that says:
Error: Request failed with status code 500

That 500 means the backend crashed with an unhandled exception. It’s not a validation error (400/403/etc) and it’s not a permissions error. It’s “the server threw an exception in Python and we didn’t catch it.”

Why that matters:

A proper business rule like “you can’t issue VAT invoice because VAT is disabled” should come back as 400 or 403 with a readable detail.

A 500 means the code hit something like NoneType access, bad math, missing required field, etc.

The most common place this blows up (given your data model) is VAT math.

Here’s the pattern I’ve seen in systems like yours:

Frontend always sends line items with fields like quantity, unit_price, maybe tax_rate or tax_code.

Backend always tries to calculate:

line subtotal

VAT amount = subtotal × tax_rate

invoice totals (net, VAT total, grand total)

BUT: when the company is not VAT registered (vat_enabled = False in CompanyDB), you either:

don’t send tax_rate / tax_code at all, or

send something like null.

If the backend code assumes those are always there (e.g. does Decimal(item["tax_rate"]) or classifies invoice as "380" and then tries to validate TRN, etc.), it will explode and return 500 instead of something graceful.

So what’s probably happening for you right now in Scenario 1:

You’re creating what should be a no-VAT / out-of-scope invoice.

The backend still runs VAT logic (maybe still treating it like a Tax Invoice).

That logic expects VAT fields (TRN, tax code/category, etc.), but those are missing because this company has vat_enabled = False.

Boom → unhandled exception → 500.

In other words:
The backend is not cleanly handling “VAT disabled” when calculating totals or validating invoice type.

How to confirm quickly:

Open DevTools → Network.

Click the failing POST /invoice (or similar) request.

Look at the Response tab.

If it’s completely empty or it's an HTML stacktrace → that’s the 500.

Look at the Request Payload you sent.

Check if you’re sending tax_code, tax_rate, etc. Are they null / missing?

That will tell you exactly which field it choked on.

How to fix (backend side):

In your invoice creation endpoint, before doing any VAT math:

Check the company that’s issuing the invoice.

If company.vat_enabled is False, force:

invoice_type = "480" (Commercial / Out of Scope),

tax_rate = 0,

tax_code = "O" / “Out of scope” for every line item.

Skip TRN validation and VAT summary lines entirely.

Guard all VAT calculations with if company.vat_enabled:.

How to fix (frontend side, quick patch if you don’t want to touch backend yet):

When VAT is OFF:

Still send tax_rate: 0 and tax_code: "O" or whatever your backend considers “out of scope / no VAT”.

Send an invoice_type that matches “Commercial Invoice / Out of Scope,” not “Tax Invoice”.

Send totals that already assume 0 VAT.

This prevents the backend from getting undefined / null and falling over.

This is safer than sending “no tax fields at all,” because right now missing fields is what’s blowing it up.

Scenario 2: Company with VAT enabled, issuing VAT Invoice

You said:

“The second scenario once the VAT is enabled, so the business can use more invoices such as VAT Invoice. check the attached error”

Since the screenshot you attached is the 500 popup, I’ll assume you're seeing the same modal even with VAT turned on.

If VAT is enabled (vat_enabled = True for that company in CompanyDB), the backend logic likely also enforces other UAE rules:

Company must have a valid TRN (Tax Registration Number).

Invoice lines must include valid UAE tax category codes (like standard rate ‘S’ 5%, zero-rated ‘Z’, etc.).

Totals must include VAT breakdown.

Those codes are referenced in InvoiceType, TaxCategory, and UAE VAT utilities in your repo. 
GitHub

So in VAT-enabled mode, you’ll get a 500 if, for example:

The company is marked vat_enabled = True, but trn in the DB is still empty / invalid.

You’re trying to create a TAX_INVOICE ("380") but one of the line items has no tax_code or an invalid code.

The math for VAT totals or QR-code hash generation chokes on None.

Again: that should have been a 400 (“TRN required for VAT invoice”), but if the code doesn’t explicitly raise HTTPException(status_code=400, detail="...") and instead just assumes TRN exists and uses it, you get 500.

How to test:

On the VAT-enabled company record in the DB:

Make sure trn is populated and valid.

On the invoice you're creating:

Make sure each line item has a tax category and tax rate that matches UAE VAT expectations (like 5% for standard-rated domestic supply).

Try again.

If it suddenly succeeds, that was the root cause.

So what needs to be fixed (action list you can do right now)
1. Check / fix company data

For each company in your database (companies table, model CompanyDB):

If the business should NOT charge VAT:

vat_enabled should be 0 / false.

trn can be NULL.

If the business SHOULD charge VAT:

vat_enabled should be 1 / true.

trn must be filled with a valid UAE TRN number.

Those fields exist in your CompanyDB model. 
GitHub

If vat_enabled = True but trn is missing, that’s a red flag and likely to cause a 500 at invoice creation.

2. Match the invoice type to VAT status

When you save the invoice from the UI:

For a non-VAT-registered company:

Use “Commercial Invoice / Out of Scope” (code "480", usually no VAT section on the PDF).

Include tax_rate: 0, tax_code: "O", totals without VAT.

For a VAT-registered company:

Use “Tax Invoice” (code "380").

Include tax breakdown per line, VAT % (5% etc.), and make sure company TRN is set.

If the UI currently always defaults to “Tax Invoice” even for a company with vat_enabled = false, the backend will be confused. Update the frontend so the invoice type dropdown respects the company’s VAT status.

3. Look at the server logs for the stacktrace

Right now you’re only seeing “status code 500” in the browser. The real reason is in your FastAPI/Uvicorn console output.

On the machine running the backend:

Check the terminal logs right after you reproduce the error.

You’ll see a Python traceback with the exact line that exploded (for example, KeyError: 'tax_rate' or AttributeError: 'NoneType' has no attribute 'strip').

That line will immediately tell you which field is missing in the request and confirm the theory.

Once you know that line, you can add a safe guard in the backend:

if not company.vat_enabled:
    # Force no-tax defaults so we don't crash
    line_tax_rate = 0
    line_tax_code = "O"  # Out of scope
else:
    # Normal VAT logic
    ...

4. Long-term: return 400 instead of 500

Wrap the VAT validation + totals calculation in try/except, and if something's invalid just raise:

from fastapi import HTTPException
raise HTTPException(status_code=400, detail="This company is not VAT-registered. Please select 'Commercial Invoice' instead of 'Tax Invoice'.")


That way the frontend will show a friendly message instead of “500”.

Bottom line

The 500 is not about authentication — it’s the backend crashing during invoice creation.

The crash is almost certainly happening when the invoice payload doesn't match what the backend expects for that company’s VAT status.

VAT OFF company → backend still tries to do VAT math or TRN logic.

VAT ON company → backend expects valid TRN / tax codes but they’re missing.

Fixes:

Make sure the company record and the invoice type line up with each other.

When VAT is OFF, send invoice as “Commercial / Out of Scope,” with explicit zero tax fields instead of leaving them null.

When VAT is ON, make sure TRN + tax details are included.

Capture the traceback in the FastAPI logs so you can harden that endpoint and replace 500 with a clean 400.
